AppSim-Bench Developer Guide

How to build a simulated app using AI-assisted development (Claude Code).

Prerequisites
  • Claude Code (CC) installed and configured.
  • Android Studio installed with a working emulator or connected device.
  • Git configured with push access to your GitHub repository.
  • The Android template project (android_template.7z) — a blank Kotlin/Compose starter project provided by AppSim-Bench.

Overview

Each simulated app in AppSim-Bench is a standalone Android project that reproduces task-relevant UI flows from a real commercial app, with controllable backend data. The development workflow is human-led, AI-assisted: you specify what to build, and a coding agent (Claude Code) generates the implementation. You then inspect, run, and correct iteratively until the app matches the benchmark specification.

The high-level pipeline is:

  1. Set up the template project in a Git repository.
  2. Design your tasks — these determine which pages and features are needed.
  3. Define a page tree (navigation structure).
  4. Model the data structures required for task verification.
  5. Develop iteratively: describe one page at a time, provide a reference screenshot, let CC implement, verify, and commit.

Core Principles

Principle 1 — Always verify manually.
After every AI-generated change, build and run the project on an emulator. If anything is broken, feed the error back to CC and let it fix the issue before moving on.
Principle 2 — Commit frequently.
Before asking CC to make a new change, commit the current working state. This ensures you can always roll back if the AI introduces regressions.
Git saves your progress. Committing often is cheap — losing a working state is expensive.

1Project Setup

  1. Create a new empty repository on GitHub.
  2. Clone it locally and extract the Android template into the repo root.
  3. Push the initial template commit.

Create a file called requirements.md at the project root. This file is where you describe development instructions for CC throughout the process.

As your first task, ask CC to rename the project from the default (test05) to a meaningful name, e.g. MyWechat:

Rename the project from "test05" to "MyWechat".
Replace all references to test05 with MyWechat. Build successfully before handing off.

Use Plan mode in CC: ask it to read requirements.md, produce a plan, review the plan, then let it execute.

2Task Design

Tasks are the benchmark's atomic units. Each task is a natural-language instruction that a GUI agent should be able to complete (e.g., "Send a message to Zhang Xiaoming saying hello"). The key insight is:

Task design defines your development scope.
Once you know which tasks the benchmark covers, you know exactly which pages must be fully interactive, which only need a static entry point, and which can be omitted entirely.

For example, if your only task for a WeChat simulator is "Send a message to X", then:

  • The Chat tab and Chat detail page need full interaction logic.
  • The Contacts tab needs to display contact entries (they are targets for messaging).
  • The Discover tab and Me tab only need to look correct — buttons don't need to do anything.
  • Features like "Scan QR", "Mini Programs", "Moments" can be omitted.

Simplification guidelines

  • Feature simplification: Only implement features that tasks touch. E.g., messaging supports text and images only — no voice, video calls, or location sharing.
  • UI simplification: Preserve the layout and visual structure of the real app, but unused detail elements (decorative badges, feature icons that tasks never activate) can be dropped.
  • The goal is "visually realistic at a glance, functionally scoped to the task set."

3Page Tree Design

The page tree is a JSON structure that defines which screens (Activities/Composables) exist in your app and how they relate to each other. It prevents the AI from creating a monolithic file and ensures a clean navigation graph. 

{
  "MainActivity": [
    "ChatTab",
    "ContactTab",
    "DiscoverTab",
    "MeTab"
  ],
  "ChatTab": ["ChatDetail"],
  "ContactTab": ["ContactDetail"]
}

The page tree grows incrementally

You don't need to define every page upfront. Start with top-level tabs, mark the one you're currently building with a // now todo annotation, and expand as you go: 

{
  "MainActivity": [
    "ChatTab",       // now todo
    "ContactTab",
    "DiscoverTab",
    "MeTab"
  ]
}

Once ChatTab is done, add its children and move the marker:

{
  "MainActivity": ["ChatTab", "ContactTab", "DiscoverTab", "MeTab"],
  "ChatTab": ["ChatDetail"]  // now todo
}

4Data Modeling

AppSim-Bench uses outcome-based evaluation. To verify that a task was completed correctly, you need observable signals stored in JSON files — not a database. Design data structures that capture the minimal state required to verify your tasks.

Example prompt for CC:

I need to verify GUI agent task completion. Design data structures for
task-relevant signals. For example:
- To verify "like a post", I need a likes list per post.
- To verify "send a message", I need a message history.

## My tasks:
{paste your task list here}

## Requirements:
1. Design only what my task list requires — nothing extra.
2. Place Kotlin data classes in app/src/main/java/com/example/MyWechat/model/
3. Only define data structures — no verification logic yet.

Initial data

After data structures are defined, populate initial data as JSON files under app/src/main/assets/data/. Text content (chat messages, contact names, etc.) can be AI-generated. Image assets (avatars, product photos) should be placed in a dedicated folder (e.g., app/src/main/assets/avatar/).

5Iterative Development

With the project, page tree, data model, and reference screenshots in place, development proceeds one page at a time:

  1. Take a screenshot of the real app's corresponding page. Save it in a UIReference/ folder, named to match the page tree node (e.g., UIReference/ChatTab.jpg).
  2. Write a requirements block in requirements.md describing the page in detail.
  3. Invoke CC in Plan mode: ask it to read requirements.md and implement the page.
  4. Review the plan, then let CC execute.
  5. Build and run on the emulator. If something is wrong, describe the issue to CC and iterate.
  6. Commit once the page is satisfactory.
  7. Move to the next page — update the // now todo marker.

Example requirements block

## Page tree
```json
{
  "MainActivity": ["ChatTab", "ContactTab", "DiscoverTab", "MeTab"],
  "ChatTab": ["ChatDetail"]  // now todo
}
```

## Reference screenshot
**UIReference/ChatTab.jpg**

## Current task
Design the ChatTab page. Elements:
1. Top bar: search button, "+" button.
2. Chat list: each entry shows avatar, contact/group name, last message
   preview, and timestamp (format: MM.DD HH:MM).
3. Image messages display as "[Image]".
4. No "send failed" indicator (simplification).
5. No voice messages (simplification).

Refinement cycle

After the initial implementation, inspect the result and provide corrections. Be specific:

Issues with current ChatTab:
- Avatars are not loading. Check asset paths under app/src/main/assets/avatar/.
- Only 4 conversations shown — increase to 8.
- Contact names look fake ("User1"). Use realistic Chinese names.
- Add at least one group chat.

Repeat until the page matches the reference screenshot closely enough for the benchmark's visual-realism standard.

Summary: The development workflow is a tight loop of specify → generate → verify → commit → expand. Each iteration adds one page or refines one aspect, keeping the project always in a buildable, runnable state.
